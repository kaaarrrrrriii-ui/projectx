# Новые API и backend-задачи для кабинета эксперта

Дата анализа: 10.09.2026  
Основание: коммит `ea05663` (`Кабинет эксперта`) после обновления ветки `main`.

## Что изменилось в проекте

Во frontend появился кабинет эксперта:

- `/expert` — главная и метрики;
- `/expert/queue` — очередь новых обращений;
- `/expert/assigned` — обращения в работе;
- `/expert/returns` — повторные обращения;
- `/expert/requests` — запросы эксперта;
- `/expert/appeals/{track}` — карточка, чат, ответ, заметка и смена статуса;
- `/expert/appeals/{track}/assign` — выбор исполнителя;
- `/expert/analytics` и `/expert/exports` — аналитика и выгрузки.

Сейчас все эти экраны получают данные из `expert-data.ts` и меняют только локальное состояние. В backend нет маршрутов `/api/expert/*`. Авторизация уже реализована через JWT, но операторские ручки разрешены только ролям `operator` и `admin`.

## Общие правила для expert API

- Все ручки ниже требуют `Authorization: Bearer <token>` и роль `expert` или `admin`.
- Для эксперта сервер всегда берёт `worker_id` из JWT. Передавать его с клиента нельзя.
- Эксперт видит полную карточку только при активном назначении в `tickets_workers`. Если очередь новых действительно должна быть общей, до принятия обращения лучше возвращать сокращённую карточку без файлов, контактов и переписки.
- В ответах API используются строковые значения: `standard`, `urgent`, `new`, `assigned`, `in_progress`, `needs_clarification`, `answer_ready`, `returned` и т. д.
- Пагинация: `page` по умолчанию `1`, `limit` по умолчанию `20`, максимум `100`.
- Каждая смена статуса, назначение, ответ и запрос должны записываться в `ticket_events` либо в отдельный журнал событий соответствующей сущности.

## Предлагаемые ручки

### 1. Профиль эксперта

`GET /api/expert/me`

Нужен для имени и специализации в боковом меню, а также для показа нагрузки.

```json
{
  "id": 7,
  "full_name": "Олег Зетник",
  "role": "expert",
  "expert_group": { "id": 2, "title": "Буллинг" },
  "active_tickets": 3,
  "max_tickets": 7,
  "avg_rating": 4.8
}
```

Альтернатива: расширить существующий `GET /api/auth/me`, но expert-поля лучше не добавлять всем ролям без необходимости.

### 2. Главная эксперта

`GET /api/expert/dashboard?date_from=2026-09-04&date_to=2026-09-10`

```json
{
  "new_count": 10,
  "urgent_count": 5,
  "overdue_count": 3,
  "returned_count": 3,
  "processed_count": 67,
  "weekly": [
    { "date": "2026-09-10", "assigned": 4, "answered": 3, "closed": 2 }
  ]
}
```

Все показатели считаются только для текущего эксперта. До реализации надо зафиксировать SLA, по которому обращение считается просроченным; сейчас UI подразумевает 24 часа, а backend это правило не хранит.

### 3. Списки обращений

`GET /api/expert/tickets`

Параметры:

```text
queue=available|assigned|returned
search=
category_id=
applicant_type=
priority=
status=
page=
limit=
```

```json
{
  "items": [
    {
      "track_id": "ОТК-ABCD-2345",
      "category": { "id": 2, "name": "Кибербуллинг" },
      "applicant_type": "schoolchild",
      "priority": "urgent",
      "status": "assigned",
      "created_at": "2026-09-10T07:55:00Z",
      "waiting_seconds": 720,
      "is_overdue": false,
      "is_responsible": true
    }
  ],
  "total": 1,
  "page": 1,
  "limit": 20
}
```

Семантика очередей:

- `available` — новые обращения категорий, связанных с группой эксперта, только если разрешено самостоятельное принятие;
- `assigned` — активные назначения текущего эксперта;
- `returned` — возвращённые обращения, где текущий эксперт снова назначен оператором.

### 4. Карточка обращения

`GET /api/expert/tickets/{track_id}`

Ответ должен включать:

- трек-номер, дату, категорию, тип заявителя, приоритет и статус;
- исходное сообщение;
- вопросы и ответы;
- доступные вложения без `storage_key`;
- историю публичного чата;
- активного ответственного и соисполнителей;
- внутренние заметки, доступные сотрудникам;
- причину и дату возврата;
- `allowed_actions`, чтобы frontend не вычислял права по статусу.

```json
{
  "track_id": "ОТК-ABCD-2345",
  "status": "in_progress",
  "priority": "urgent",
  "created_at": "2026-09-10T07:55:00Z",
  "category": { "id": 2, "name": "Кибербуллинг" },
  "applicant_type": "schoolchild",
  "description": "Текст обращения",
  "clarifications": [
    { "question_id": 1, "question": "Где это происходит?", "answer_id": 3, "answer": "Онлайн" }
  ],
  "attachments": [
    { "id": 12, "name": "screenshot.png", "mime_type": "image/png", "size_bytes": 84211 }
  ],
  "messages": [],
  "workers": [],
  "notes": [],
  "allowed_actions": ["start", "send_answer", "add_note", "create_request"]
}
```

### 5. Скачать вложение из карточки

`GET /api/expert/tickets/{track_id}/attachments/{attachment_id}`

Сервер проверяет активное назначение эксперта на обращение, принадлежность файла обращению и отдаёт бинарный файл с безопасным `Content-Disposition`. Публичную ручку скачивания по одному знанию трек-номера для кабинета сотрудника переиспользовать не следует.

### 6. Начать работу или запросить уточнение

`POST /api/expert/tickets/{track_id}/transition`

```json
{ "status": "in_progress" }
```

Для эксперта разрешить только явные переходы:

- `assigned -> in_progress`;
- `in_progress -> needs_clarification`;
- `needs_clarification -> in_progress` после ответа заявителя.

`answer_ready` устанавливается отправкой ответа, `returned` — действием заявителя, завершение и отклонение остаются за заявителем/оператором. Текущий dropdown с произвольным выбором `Новое`, `Закрыто` и других статусов нужно ограничить на frontend.

### 7. Внутренние заметки

`POST /api/expert/tickets/{track_id}/notes`

```json
{ "text": "Нужно уточнить контекст ситуации" }
```

```json
{
  "note": {
    "id": 41,
    "text": "Нужно уточнить контекст ситуации",
    "author": { "id": 7, "full_name": "Олег Зетник" },
    "created_at": "2026-09-10T09:10:00Z"
  }
}
```

Для нормального аудита заметки лучше делать неизменяемыми записями `messages.type = internal_note`. Если UI должен редактировать одну заметку, потребуется отдельная таблица или явный `PATCH` с историей изменений.

### 8. Отправить ответ заявителю

`POST /api/expert/tickets/{track_id}/messages`

```json
{ "text": "Бережный и понятный ответ заявителю" }
```

```json
{
  "message": {
    "id": 52,
    "type": "specialist",
    "text": "Бережный и понятный ответ заявителю",
    "created_at": "2026-09-10T09:20:00Z"
  },
  "ticket_status": "answer_ready"
}
```

Тип сообщения и автор определяются сервером по JWT. Создание сообщения, смена статуса и запись события выполняются в одной транзакции. Отвечать может только активно назначенный эксперт. Первый ответ должен давать событие для аналитики.

### 9. Создать запрос коллеге или оператору

`POST /api/expert/tickets/{track_id}/requests`

```json
{
  "recipient_user_id": 11,
  "request_type": "consultation",
  "reason": "Нужна консультация по обращению"
}
```

Допустимые типы на текущем UI: `consultation`, `legal`, `operator`. Для `operator` можно разрешить `recipient_user_id = null` и направлять запрос в общую операторскую очередь.

```json
{
  "request": {
    "id": 83,
    "status": "pending",
    "created_at": "2026-09-10T09:25:00Z"
  }
}
```

Свободное поле «Фамилия и инициалы» на frontend нужно заменить выбором пользователя по `id`; иначе невозможно надёжно определить адресата.

### 10. Список запросов

`GET /api/expert/requests?status=pending&page=1&limit=20`

```json
{
  "items": [
    {
      "id": 83,
      "track_id": "ОТК-ABCD-2345",
      "category": { "id": 2, "name": "Кибербуллинг" },
      "applicant_type": "schoolchild",
      "priority": "urgent",
      "request_type": "consultation",
      "status": "pending",
      "recipient": { "id": 11, "full_name": "Анна Петрова" },
      "created_at": "2026-09-10T09:25:00Z"
    }
  ],
  "total": 1,
  "page": 1,
  "limit": 20
}
```

Если получатель должен отвечать на запрос внутри системы, дополнительно понадобятся:

- `GET /api/expert/requests/{request_id}`;
- `POST /api/expert/requests/{request_id}/reply`;
- `POST /api/expert/requests/{request_id}/complete`.

Текущий экран ответа на запрос не содержит, поэтому эти три ручки можно вынести во второй этап.

### 11. Аналитика и выгрузка эксперта

`GET /api/expert/analytics?date_from=2026-09-01&date_to=2026-09-10`

`GET /api/expert/reports?date_from=2026-09-01&date_to=2026-09-10&format=csv`

Формат можно оставить совместимым с операторскими ответами, но выборка должна быть ограничена обращениями текущего эксперта. Выгрузка остаётся обезличенной. Переиспользовать `/api/operator/*` с расширением доступа нельзя: это даст эксперту агрегаты и обращения других сотрудников.

## Backend-задачи

### BE-EXP-01. Каркас expert-модуля и авторизация — P0

- Добавить `ExpertHandler`, `ExpertService`, `ExpertRepository` и регистрацию маршрутов.
- Добавить `RequireExpert` с разрешением ролям `expert/admin`.
- Реализовать единый guard активного назначения и закрыть IDOR по чужому `track_id`.
- Покрыть `401`, `403`, чужое назначение и роль оператора handler-тестами.

### BE-EXP-02. Профиль и dashboard — P1

- Реализовать `/api/expert/me` и `/api/expert/dashboard`.
- Считать нагрузку по активным строкам `tickets_workers`, а не хранить отдельным числом.
- Зафиксировать SLA просрочки и границы недельного периода в `Asia/Yekaterinburg`.
- Добавить repository/service/handler-тесты на пустую статистику и границы дат.

### BE-EXP-03. Очереди эксперта — P0

- Реализовать списки `available`, `assigned`, `returned`, серверные фильтры и пагинацию.
- Ограничить `assigned/returned` текущим `worker_id` и `actual = true`.
- Не возвращать закрытые назначения как активные.
- Добавить индексы под выборку по `worker_id`, `actual`, `status`, `created_at`.
- Протестировать отсутствие данных другого эксперта.

### BE-EXP-04. Карточка и защищённые вложения — P0

- Собрать DTO карточки из `tickets`, `categories`, первого applicant-message, `QA`, `questions`, `answers`, `messages`, `attachments`, `tickets_workers`, `users` и `ticket_events`.
- Реализовать `allowed_actions` из роли, назначения и текущего статуса.
- Сделать отдельную employee-проверку скачивания вложений.
- Добавить интеграционные тесты полного обращения и попытки скачать чужой файл.

### BE-EXP-05. Машина статусов эксперта — P0

- Реализовать только допустимые переходы через `/transition`.
- Блокировать изменения при неактивном назначении и гонке двух запросов.
- Записывать `ticket_events` с `actor_user_id`, `from_status`, `to_status`.
- Добавить табличные тесты всех разрешённых и запрещённых переходов.

### BE-EXP-06. Заметки эксперта — P1

- Сохранять заметки как `messages.type = internal_note` с автором.
- Добавить `author_user_id` в `messages`: текущая схема не позволяет определить автора заметки или ответа.
- Не включать внутренние заметки в публичный `/api/tickets/{track_id}/chat`.
- Протестировать изоляцию внутренних сообщений от заявителя.

### BE-EXP-07. Ответ заявителю — P0

- Создавать сообщение `specialist`, определяя автора по JWT.
- Атомарно переводить обращение в `answer_ready` и создавать событие `specialist_answered`.
- Запретить ответ неназначенному эксперту и ответ в финальных статусах.
- Добавить идемпотентность либо защиту UI от двойной отправки.
- Покрыть транзакцию repository-интеграционным тестом.

### BE-EXP-08. Запросы эксперта — P1

- Добавить миграцию `expert_requests`: `id`, `ticket_id`, `sender_user_id`, `recipient_user_id`, `request_type`, `reason`, `status`, `created_at`, `resolved_at`.
- Добавить constraints для типов/статусов и индексы по отправителю, получателю и статусу.
- Реализовать создание и список запросов.
- Проверять, что отправитель назначен на обращение, а получатель — активный сотрудник подходящей роли.
- Записать событие создания запроса и покрыть сценарии тестами.

### BE-EXP-09. Назначение исполнителя из кабинета эксперта — P2, после решения по ролям

Текущий UI позволяет эксперту добавлять или менять исполнителя. Это конфликтует с существующим правилом, где назначения выполняет оператор.

Рекомендуемый вариант: убрать этот экран у эксперта, а потребность в помощи закрыть через `expert_requests`. Если бизнес подтверждает право эксперта назначать коллег:

- добавить отдельные `/api/expert/tickets/{track_id}/eligible-workers` и `/workers`;
- разрешить только добавление соисполнителя, не смену ответственного;
- проверить принадлежность к обращению, лимит нагрузки и записать аудит;
- не расширять права существующих `/api/operator/*`.

### BE-EXP-10. Персональная аналитика и отчёты — P2

- Переиспользовать расчёты операторской аналитики с обязательным фильтром `worker_id` из JWT.
- Считать назначения и ответы по `ticket_events`/автору сообщений, а не по текущему ответственному.
- Реализовать обезличенные CSV/XLSX без треков, текстов, контактов и имён.
- Проверить часовой пояс, диапазоны дат и отсутствие чужих данных.

### FE-EXP-01. Подключение frontend к API — после P0 backend

- Удалить `expert-data.ts` и загрузить профиль, dashboard, списки и карточку с backend.
- Передавать JWT, обрабатывать `401/403/404/409`, загрузку и пустые состояния.
- Ограничить dropdown статусов значениями из `allowed_actions`.
- Сделать имена вложений ссылками на защищённую ручку.
- После ответа обновлять карточку ответом сервера, а не локальным `Date.now()`.
- Заменить ввод ФИО адресата запроса на выбор `recipient_user_id`.

## Необходимые изменения схемы

Обязательные:

1. `messages.author_user_id NULL REFERENCES users(id)` — автор экспертного ответа, внутренней заметки или сообщения оператора. Для сообщения заявителя остаётся `NULL`.
2. Таблица `expert_requests` для запросов и их статусов.
3. Индекс `tickets_workers(worker_id, actual, ticket_id)` для кабинета эксперта.

Желательные:

1. `attachments.message_id` — если экспертам позже разрешат прикладывать файлы к конкретным ответам. Сейчас вложение связано только с обращением.
2. SLA-настройка либо зафиксированная серверная константа для `is_overdue`.
3. `idempotency_key` для отправки публичного ответа, если frontend допускает повтор запроса.

## Вопросы, которые блокируют окончательный контракт

1. Эксперт видит общую очередь новых обращений и может сам взять обращение или только обращения, назначенные оператором?
2. Эксперт действительно может менять ответственного/добавлять исполнителя или кнопка должна создавать запрос оператору?
3. Что именно означает раздел «Запросы»: исходящие запросы эксперта, входящие запросы коллег или оба вида?
4. Кто является адресатом типов `consultation`, `legal`, `operator`, и требуется ли ответ внутри системы?
5. Какие действия эксперта дают статусы «Нужна консультация» и «Нужен повторный ответ»?
6. Нужны ли вложения в ответах эксперта? Текущий новый UI их не предлагает.
7. Аналитика эксперта должна показывать только личные показатели или показатели всей экспертной группы?
8. Сохраняем ли историю выгрузок? Текущий backend генерирует файлы сразу и таблицы выгрузок не имеет.
