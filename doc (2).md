## 1. Публичная часть

Страница: `/appeal/t1opics`

Это необходимо, потому что по ТЗ категории редактирует администратор. Сейчас они захардкожены в `frontend/src/features/appeal/categories.ts`.

### 3. Кнопка «Отправить обращение»

Страница: `/appeal/attachments`

Предлагаемая ручка:

`POST /api/tickets`

Формат: вероятнее всего `multipart/form-data`, поскольку вместе с обращением передаются файлы.

Запрос должен содержать:

```text
applicant_type
category_id
description
answers[question_id]
attachments[]
crisis_contact — опционально
```

Ответ:

```json
{
  "track_id": "ОТК-ABCD-2345",
  "status": "new",
  "created_at": "2026-09-09T14:48:00Z",
  "crisis_detected": false,
  "crisis_contacts": []
}
```

Предполагаемые источники хранения:

- основная запись — `tickets`;
- тип заявителя — предположительно `tickets.morda_type`;
- описание — предположительно первая запись в `messages`;
- ответы — `"QA"`;
- файлы — `attachments`;
- добровольный кризисный контакт — `crisis_contact`;
- трек-номер генерируется уже существующим `GenerateTrackCode()`.

При создании сервер должен сам установить:

- `priority` — стандартный;
- `status` — новое;
- `return_count` — `0`;
- `created_at`;
- `track_id`.

Сейчас данные между страницами формы не сохраняются вообще, а финальная страница показывает захардкоженный трек-номер.

### 4. Кнопка «Проверить» на `/status`

Предлагаемая ручка:

`GET /api/tickets/{track_id}/status`

Либо `POST /api/tickets/status`, если трек-номер не хочется помещать в URL и серверные логи.

Ответ минимум:

```json
{
  "track_id": "ОТК-ABCD-2345",
  "status": "answer_ready",
  "created_at": "2026-09-09T14:48:00Z",
  "category": {
    "id": 2,
    "name": "Кибербуллинг"
  },
  "can_open_chat": true,
  "can_complete": true,
  "can_return": true
}
```

Источники:

- `tickets.track_id`
- `tickets.status`
- `tickets.created_at`
- `tickets.category_id`
- `categories.id`
- `categories.name`

Ты привёл именно эти три поля: `tickets.status`, `tickets.created_at`, `categories.name`. Я предлагаю дополнительно возвращать признаки разрешённых действий, чтобы клиент не угадывал их по числовому статусу.

Для этой ручки обязательно понадобится ограничение попыток: по ТЗ не более примерно 5 проверок в минуту с одного адреса.

### 9. Кнопка «Нет» / «Это не помогло» и «Отправить»

Предлагаемая ручка:

`POST /api/tickets/{track_id}/return`

Запрос:

```json

```

Результат:

- `tickets.status` → возвращено;
- `tickets.return_count` увеличивается;

Проблема: в миграции нет отдельного места для причины возврата. Теоретически её можно записать в `messages`, но тогда нужно определить специальное значение `messages.type`.

## 6. Проблемы текущей миграции

До проектирования DTO нужно договориться о значениях:

- Нет справочника или констант для `tickets.status`.
- Нет справочника для `tickets.priority`.
- Не определено назначение `tickets.morda_type`; предполагаю, что это тип заявителя.
- Не определены значения `messages.type`.
- Нет истории смены статусов и исполнителей.
- Нет времени принятия обращения и времени первого ответа.
- Нет места для причины отклонения и причины возврата.
- Нет признака кризисного обращения; есть только отдельный контакт.
- Нет хранения произвольной темы пользователя.
- `attachments.width` и `height` обязательны и больше нуля, поэтому PDF туда нормально не записать.
- Backend сейчас обрабатывает только JPEG/PNG, хотя frontend разрешает PDF и любые `image/*`.
- На frontend ограничение выглядит как «до 10 МБ каждый», а backend ограничивает 10 МБ на всю пачку.
- `reviews` позволяет несколько оценок одного обращения — уникального ограничения по `ticket_id` нет.
- `tickets.track_id` хранится открытым текстом, хотя в сервисе уже есть функция `HashTrackCode`; отдельной колонки для хеша нет.
- Не хватает журнала административных действий, обязательного по ТЗ.
